## What Lovable manages

Rules outside this block are the project's own. Change the pieces below in
Lovable, not by hand. With the [Lovable MCP](https://mcp.lovable.dev)
connected, `send_message` asks Lovable to do it; otherwise ask the user to
use the editor.

- **Database.** Do not add or edit `supabase/migrations/` or `drizzle/`.
  Ask Lovable to change the schema.
- **Generated files.** Do not edit a file whose header says it is automatically
  generated.
- **AI gateway.** Keep model calls on Lovable's gateway, and keep
  `LOVABLE_API_KEY` out of browser code.
- **Connectors.** Lovable provides native connectors. `list_connectors` shows
  which are enabled; `add_connector` only returns the dashboard link. When a
  connector is enabled, calls go through the connector gateway and need
  `LOVABLE_API_KEY`. When Lovable does not provide one, users can bring their
  own key and store it in Secrets.
- **Secrets.** Lovable manages them. Do not put secret values in the repo.
<!-- LOVABLE:END -->

- Offline screen access is local convenience only, not a trusted authorization boundary; credentials are PBKDF2 hashes and local roles are separate from profiles because no hosted identity exists.
- Persist only the active profile ID locally and resolve its current role at hydration; explicit logout clears it and storage events synchronize access changes across tabs, avoiding reload-driven logouts without persisting credentials in the session.
- Staff UI mounts separately from the owner ledger and only projects allowed product/stock fields; never render owner financial tables for staff.
- Backups contain versioned business tables, not credentials or roles; validate all rows before replacing local data.
- Offline service workers are generated by vite-plugin-pwa and registered only through the preview-safe wrapper.
- Customer details use the existing customers table through an owner-only CustomerPanel; optional added fields preserve existing records and backup compatibility.
